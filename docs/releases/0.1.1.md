# Uberhar 0.1.1 — sustained diagnostics across more games

<!-- AstraEH: Small diagnostic iteration; preserve the successful Native beta renderer. -->

0.1.0 testing keeps Fire Emblem Awakening near full normal speed and reduces its
vertex-stage cost per input by about 10%. Ocarina averages 99.912% normally and
374.628% in the tested fast-forward segment. Awakening's fast averages are lower
than 0.0.15 with different scene/vertex coverage, so total headroom improvement is
not yet established. Sonic exposes a different problem: sustained high draw/vertex
workload after generic shader compilation has already finished.

## Changes

- **Keep detailed sampling alive throughout a run.** Sonic exhausted the old
  lifetime quota before most racing and before the resolution change. Admit one
  rotating-input sample per 50 ms using the existing draw timestamp, without
  catch-up bursts after pauses. Ordinary per-vertex execution remains untimed.
- **Measure selected full batches.** Separate setup, complete CPU vertex work and
  the following DrawTriangles host call, with input/invocation counts. These raw
  samples guide the next optimization; they are not GPU timings or whole-run totals.
- **Record launch context once.** Log selected model, core count, CPU clock setting,
  title capability requests and kernel 804 metadata. New 3DS model selection is
  different from a physical console's forced Clock+L2 setting.
- **Reduce repeated service-log noise.** Preserve the exact GetFriendKeyList reply,
  but log first-four/power-of-two request summaries and final counts. The supplied
  13,141 warnings would become 15 warnings plus one total. They occurred outside
  sustained racing, so this is not presented as a fix for Sonic's race speed.

Native vertex diagnostics become schema 2. Renderer schema 12, frame schema 2 and
fragment ABI 5 remain unchanged. No shader arithmetic, cache/FIFO behavior, draw
order, graphics profile, console-model policy or guest service response changes.
New sections carry AstraEH attribution and diagnostic calls carry `AstraEH Log Line`.
Android permissions, dependencies, package identity, Beta label and signing policy
are retained. See the [analysis](../UBERHAR_LOG_ANALYSIS_0.1.0.md) and
[diagnostic definitions](../UBERHAR_DIAGNOSTICS.md).

## Next test

Install as an update. Start with Sonic in **Native, 2x, New 3DS mode on, CPU clock
100%**, then run a warm race without changing resolution/backend. If practical,
exit, switch **only New 3DS mode off** under System settings, relaunch from a normal
in-game save and repeat that race warm. Keep all other settings the same. Restore
your usual model afterward if changing the global setting. Do not load a save state
captured under the other console model for this comparison.

Export the log after exiting normally and note the race/track, model and any visual
changes. The first launch after an upgrade can invalidate compatible-module caches;
allow a warm repeat before comparing sustained speed. A short normal-speed Awakening
check is sufficient for this diagnostic iteration; all four repeated runs are optional.

Sonic is not assigned an automatic workaround. A shader-wait fix does not necessarily
fix sustained runtime cost, and a backend change has no proven benefit on this Thor.
The [automatic compatibility-profile roadmap](../UBERHAR_COMPATIBILITY_PROFILES.md)
is scheduled after 1.0.0, subject to validated title-specific evidence. This alpha
is intentionally focused in response to the owner's request.

## Validation and publication

The production host probe suite and PicaCore/Core/FRD integration syntax checks pass.
The vertex test retains 998,282 exact output comparisons and 384 FIFO/assembly cases,
and adds dense/empty draw, boundary, pause/no-catch-up and 10,000 continuing-sample
admission checks. Existing family, pipeline, profile, interpreter and frame tests
remain gates. The vertex suite also passes AddressSanitizer/UndefinedBehaviorSanitizer
(leak detection disabled), and all eight manifest-policy unit tests pass locally.
Android compilation, full shader/pixel regression, APK packaging and
pinned-certificate validation must pass in Actions before prerelease publication.
No new Thor performance result is claimed. The next full architectural review
remains after 0.1.3 by default; this results analysis does not reset that cadence.
