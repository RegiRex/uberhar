# Uberhar 0.0.10 — virtual PICA test profiles

<!-- AstraEH: Concrete release scope and device test instructions; no unmeasured speedup claim. -->

Three mutually exclusive switches now appear at the top of **Graphics**:

- **Virtual PICA: native rasterization** uses CPU-interpreted PICA vertex work and
  primary generic fragment processing. Covered draws no longer compile a competing
  specialized pipeline. Generic first-use pipelines can still pause.
- **Virtual PICA: compute rendering** uses one startup-prepared compute program for
  supported solid rectangles. Other draws use the native test route. This is a
  small first compute prototype, not a complete compute renderer.
- **Virtual PICA: automatic combination** samples GPU execution time and chooses
  between the two routes for supported rectangles. Other draws remain native.

Selecting a mode locks the remaining Graphics settings except **Internal
resolution** and **Integer scaling**. Turning the active mode off restores the
saved custom values. The three switches cannot conflict. Restart the game when
changing modes; they are disabled while a game is running.

These modes share the reference CPU vertex interpreter. They can be substantially
slower than the previous warm specialized renderer. The first compute subset may
have little or no coverage in a particular game. Full GPU vertex interpretation,
textured compute triangles and a complete generic pipeline bank remain future
work. No claim of zero compilation stalls or improved Thor performance is made.

## Test sequence

Keep **2x resolution** initially and repeat the same Awakening section:

1. Select Native. Clear the Vulkan cache using the existing procedure, play the
   section, exit normally, and repeat once without clearing it.
2. Repeat that cold/warm pair with Compute, then Automatic if practical.
3. Export the combined log. The selected mode, CPU vertex-stage cost, generic
   waits, compute coverage and sampled GPU durations distinguish the experiments.

Do not adjust Force TEV or other lower controls while a profile is selected;
the profile handles its effective settings. For a custom 0.0.9-style comparison,
turn all three top switches off and set the lower controls normally.

The 0.0.9 normal cold run spent 20.821 s waiting for pipelines versus 20.790 s in
0.0.8; its worst wait improved from 1.337 s to 1.124 s. The normal warm run had no
pipeline waits. Forced TEV's full cold run spent 50.410 s waiting. These separate
playthroughs prompted the architectural change; they are not controlled benchmarks.

New implementation sections are marked **AstraEH**. Diagnostics use the searchable
**AstraEH Log Line** marker and bounded summaries. Existing application identity,
permissions, signing continuity and Android package validation are retained.
