# Uberhar 0.1.5 — reuse exact renderer preparation

<!-- AstraEH: Remove repeated host work while retaining the released rendering decisions. -->

## Why this change

The 0.1.3 architecture review found current/historical family canonicalization,
multiple hashes and sixteen census-set lookups before every fallback pipeline
lookup. The latest Sonic test performs 12.43 million draws but encounters only
25 raw fragment families and 40 raw pipeline candidates. Reusing pure preparation
is a concrete general renderer optimization for this repeated work.

## Implementation

- Add a 256-entry, renderer-owned cache of family/census values. Compare complete
  raw FS and static pipeline representations before reuse. Hash collisions and
  evictions recompute; hashes alone never authorize reuse. Consecutive identical
  inputs avoid slot hashing as well.
- Preserve all sixteen census dimensions, historical lighting families, light
  coverage, cap behavior and observation before pipeline admission. A cache miss
  follows the released calculations; repeated insertion after eviction is safe.
- Configure against the complete device profile and extended-dynamic feature.
  Reconfigure at the only mutable profile setter; clear with title/census reset.
  Fixed storage is 213392 bytes (about 208 KiB) on the tested 64-bit host.
- Add one aggregate preparation record at existing progress/final boundaries:
  requests, hits, misses, evictions, invalidations, memory and separate hit/miss
  timing samples. Sample one request in 1024; never print per-draw text.
- Preserve AstraEH attribution and update the code map and diagnostic reference,
  including its formerly stale startup schema/ABI example.

This does not change shader arithmetic, fragment ABI 7, execution-key policy,
per-draw constants, Vulkan command ordering, readiness/failure handling, pipeline
caps, disk cache formats or driver workarounds. Renderer diagnostics advance to
16. Settings/cache schema 1 and frame schema 3 remain. Loading-time prewarming
and automatic in-game phase attribution are still separate work.

## Validation and measured limits

Passed locally: full host suite; 23318 differential preparation checks against
the released calculation path; complete input-byte mutation; forced collisions,
eviction, profile/feature/title invalidation, dynamic-state exclusion, saturated
census equality; address/undefined-behavior sanitizers; Vulkan pipeline-cache and
rasterizer integration syntax checks; whitespace checks.

The optional benchmark compares identical one-million-request streams. Median
per-request times from three runs on this host, including census updates:

| Synthetic workload | Reuse | Released path | Cached path |
| --- | ---: | ---: | ---: |
| 40 states, four consecutive repeats | 97.50% | 374.8 ns | 31.6 ns |
| 192 states, four repeats | 86.84% | 351.7 ns | 72.9 ns |
| 1024 states, four repeats | 75.34% | 373.8 ns | 126.1 ns |
| 1024 states, no consecutive repeats | 1.37% | 386.1 ns | 483.8 ns |

These measure one preparation block, not an emulator, Android or GPU benchmark.
Miss-heavy streams can cost more: the adverse case adds about 98 ns/request here.
Do not convert the repeated-state speed ratios into game-speed claims. Device
reuse and sustained speed determine acceptance; reconsider storage/admission if
misses dominate. Timing samples are deterministic and not unbiased totals.

Shader algorithms are unchanged and the differential checks compare complete
family values. Required full shader/pixel, Android build, package, signing and
prerelease gates run in Actions and remain pending at source handoff. No APK-ready
or device-speed claim is made. Build fingerprints can still require new generic
modules on the first launch after upgrading.
