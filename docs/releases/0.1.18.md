# Uberhar 0.1.18 — input correctness and failure recovery

<!-- CodexAstraUlt-2: Owner-approved fixes after the 0.1.17 source review; device results are separate. -->

## Changes

- Keep an eligible Combo draw on the CPU when an active vertex loader has zero
  stride. Native repeats the configured attribute; the inherited GPU packing
  substitutes a default. The guard preserves complete draw order and runs before
  speculative input reads or uploads. Up to four `Uberhar GPU input fallback`
  records per renderer identify whether a title encounters this case.
- Publish shader and graphics-pipeline failures as completed failures. Reject null
  shader dependencies, keep an available accurate alternative, and terminate the
  command stream when neither rendering path can execute the draw. Propagate the
  typed failure to the emulation thread, cancel later work, and drain safely without
  waiting for a GPU submission that was canceled. Android handles cache-loading and
  gameplay failures through the existing Rendering stopped outcome.
- Make log-flush barrier insertion nonblocking on both queue locks. Saturation or
  contention reports a failed flush instead of hanging before the five-second
  completion timeout. Ordinary log records retain their waiting/FIFO behavior.
- Stage interrupted text logs before rotation using a provider rename plus a small
  incident marker. The existing one-shot recovery worker performs large copies,
  synchronization, publication and legacy migration. Failed staging preserves the
  original and uses append mode; failed copies keep staged evidence for retry.
  Metadata lookup/rename and small marker writes still occur during startup.
  After interruption, the preserved text appears under `log/crashes/` when recovery
  finishes; ordinary clean-start current/previous/older rotation remains.

All new logical-section comments use **CodexAstraUlt-2**, as requested. Existing
Azahar, AstraEH and AstraPro authorship is preserved. There is no new permission,
service, continuous logging worker, public telemetry or crash-report browser.

## What this release does not establish

<!-- CodexAstraUlt-2: Do not present host reproduction or error containment as a Thor performance result. -->

The zero-stride input difference and blocked flush were reproduced on the host.
Neither is yet linked to Dark Moon's actual failing draw or crash. Driver faults,
memory pressure and other unsupported input layouts remain possible causes.
Native still uses CPU vertex processing. Combo still requires first-use generic
pipeline creation; the computed rectangle path is not a general 3D rasterizer.
No measured speed increase, Dark Moon cure or eliminated compilation waiting is
claimed. A handled Rendering stopped error preserves failure information; it does
not mean the game successfully continued through an invalid draw.

## Validation and publication

<!-- CodexAstraUlt-2: The exact source revision and all publication gates are recorded by Actions. -->

See [progress and local validation](../UBERHAR_PROGRESS.md). New regressions cover
zero-stride input parity, failure publication/canceled submissions, contended log
flush and interrupted log-staging retries. Existing shader/pixel checks, Android
compilation and JVM tests, package identity, signing and provenance remain mandatory
in the unchanged ARM64 prerelease workflow. Only the published release assets are
installable build results; source publication or a running workflow is not approval
of a finished APK. Thor/Adreno, Android provider and GammaOS validation remain device
work even when host checks pass.

## Short Thor Max test

<!-- CodexAstraUlt-2: Isolate visible correctness before requesting another prolonged failing run. -->

1. Update from the published ARM64 APK without clearing app data. Keep stock driver,
   Vulkan, resolution and speed limit identical across the comparison.
2. In Dark Moon, compare a short repeatable scene in Native and Combo. Record where
   the first visible fault appears and stop the Combo test there; no long crash
   replay is required. Keep fast-forward separate from normal-speed observations.
3. Export the relevant current/previous/older log and include the installed version,
   mode and scene. A `reason=zero_stride` record confirms this new guard was used;
   its absence does not certify all vertex layouts or diagnose a crash.
4. If Rendering stopped appears, retain that text log. If the app actually exits,
   reopen it once and retain matching files from `log/crashes/`, including any OS
   exit summary and tombstone/trace. Missing OS evidence does not rule out a crash.
5. Check one previously working game briefly, and confirm ordinary log export and
   restart still work. Performance comparisons need matched scenes and settings.
