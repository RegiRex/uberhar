# Uberhar 0.0.9

Experimental Android ARM64 alpha for Ayn Thor. Install **uberhar-0.0.9-arm64.apk**
over Uberhar after this pre-release is published. The Android, shader, package
and signing gates must all pass first.

The 0.0.8 log records more fallback reuse, but cold scheduler waiting rises from
18.957 to 20.790 seconds and the longest wait from 1.063 to 1.337 seconds. The
warm session records no waits. Crucially, **the CPU bridge serves zero draws**:
its initial admission rules exclude the pending work. The
[full analysis](../UBERHAR_LOG_ANALYSIS_0.0.8.md) distinguishes measured results
from likely causes and explains the current driver's capability limitations.

## Changes

- **Broader CPU vertex bridge coverage.** Accept triangle strips, fans and
  list-equivalent Shader topology without guest geometry shaders, in addition
  to complete lists. Both input and expanded output are capped at 4,096 vertices;
  strips/fans therefore accept at most 1,367 inputs. A ready compatible generic
  pipeline is still required, and ready GPU specialization still takes priority.
- **Explicit batch isolation.** The PICA core distinguishes a prepared bridge
  from an ordinary software draw. Bridge triangle assembly preserves the existing
  accelerated path's independent-batch behavior, including cleanup on exceptions,
  so strip/fan tails cannot keep later draws on the CPU. Ordinary software draws
  retain their persistent assembler. The generic pipeline uses list topology,
  matching the triangles actually submitted; full key validation remains.
- **Actionable rejection counts.** Aggregate coverage reports separate topology,
  too-small batches, input limits, incomplete lists and expanded-output limits.
  Seen and selected topology counters show whether the new route actually runs.
- **Whole-session worst waits.** Keep eight worst scheduler waits, including late
  events after the first-20 detail budget, and report them at normal shutdown.
  Records include renderer-relative time, draw ordinal, topology, pipeline keys,
  pending stages and selected route. A histogram covers every measured wait and
  is included in the existing bounded progress reports.

Every new diagnostic call has an adjacent **`AstraEH Log Line`** marker. There
is no per-vertex output. Progress remains at most once every five seconds, with
the clock checked once per 4,096 draws. Worst-event storage is eight records;
only actual slow waits take its short lock. See the
[diagnostics map](../UBERHAR_DIAGNOSTICS.md) for counter meanings and limits.

## Validation and limits

Local checks pass **264 production primitive-assembly comparisons**, including
indexed/repeated vertices, strip winding, repeated isolated batches, ordinary
cross-batch continuity and exception cleanup. Admission tests cover each limit
and rejection reason. Wait tests cover histogram boundaries, a new worst event
after 40 earlier events, and 4,000 concurrent records/snapshots. Existing family,
pipeline-key, first-ready/failure-selection and Android setting-key checks pass.
Native C++ syntax checks cover the changed Vulkan implementation and PICA core.
Actions repeats the full existing shader/pixel/depth and APK validation gates.

These checks do not measure Thor performance or prove whole-game CPU/GPU vertex
equivalence. The source change does not fix the inherited accelerated renderer's
documented assumption about strip/fan state across separate host draws. It keeps
bridge behavior consistent with that path; it does not clear ordinary software
assembly or introduce a global assembler reset.

CPU preparation/JIT and first-time generic pipeline creation can still stall.
The bridge remains optional and only selects a completed generic pipeline.
Startup generic-bank preparation and a GPU vertex interpreter are future work.
No new driver extensions are enabled, no driver blacklist is bypassed, and no
Android permissions, application identity or signing settings change.

## Device test

1. Use the same driver, **2x resolution**, **Hybrid TEV on**, **CPU vertex bridge
   on**, **Force TEV fallback off**, and otherwise unchanged settings.
2. Clear Awakening's **Vulkan shader cache** once. Play the same section at
   normal speed, then exit normally through the emulator menu.
3. Replay with the cache retained, exit normally and save the Current session
   log. Normal exit includes the final eight worst-wait records.
4. Mention any geometry/lighting differences and where the bad pauses occurred.
   If the result worsens, repeat separately with only **CPU vertex bridge off**
   (restart and clear before its cold run) to isolate its effect.

The startup line identifies `diagnostics=6` and
`bridge_assembly=isolated_lists_strips_fans`. Keep fast forward and 4x resolution
for a separate test. The next full architectural review is due around 0.0.10.
