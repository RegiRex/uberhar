# Uberhar 0.1.40 — prepared TEV for CPU vertex draws

<!-- CodexAstraLocal: The new tier removes repeated fragment decisions while
keeping CPU vertices on CPU and treating target performance as unmeasured. -->

Native and full Combo can use an optional fragment shader with the prepared
texture-combiner program fixed at compilation. Lighting and the other runtime
fragment controls remain dynamic. This reduces repeated per-pixel TEV selection
without requiring a saved shader cache or moving more guest vertex work to the
GPU. Native therefore gains this intermediate fragment tier; it is no longer
restricted to the generic fragment shader on every CPU draw.

A complete generic route remains available for missing, pending, failed or
capped optional entries. Combo's already-ready fully specialized CPU pipeline has
priority, and CPU demand continues to promote that full specialization while an
intermediate pipeline renders. Existing ready GPU-vertex behavior is unchanged;
creating Native's optional compiler worker cannot enable that route.

<!-- CodexAstraLocal: State exact ownership and compile budgets, including the
additional memory cost; object counts are not a Vulkan driver allocation bound. -->

An exact key owns all six prepared TEV stages, buffer timing, fragment family,
profile and CPU interface policy. Hashes only locate candidates. The existing
88-byte CPU vertex format and captured 128-byte dynamic state transport remain
unchanged. Optional compilation uses the optimized frontend and shares the
existing single optional worker with full specialization, pipeline creation and
retirement. Pending optional work never blocks selection of a ready draw route.

The CPU pipeline bank reserves eight owners and 64 lifetime attempts for full
specialization, plus eight owners and 16 attempts for the new tier. Each tier has
separate demand history and replacement pressure. In-flight, failed and retiring
owners remain charged until destruction completes; ready hits remain usable
after attempt exhaustion. The existing aggregate GPU/CPU budget still applies.
Intermediate shader modules separately allow eight owners and 16 attempts.
These additional bounded objects may increase live driver memory. Neither object
caps nor generated-source byte counters establish a driver-memory saving.

<!-- CodexAstraLocal: Explain the measured predecessor limit without treating
unmatched openings or opaque GPU samples as causal evidence for this candidate. -->

The preceding .39 cold Dark Moon controls at Vulkan 2x and a 100% limit remained
well below target: Native averaged 30.476% normal speed over 46 complete windows,
and Combo 28.763% over 49. Their slowest/best windows were 14.591%/68.868% and
16.275%/65.106%. The runs used different scene timing and observer placement;
these means are not a matched mode comparison. The new .39 CPU queue completed
129,171/129,119 packets in the respective interior report spans, all in single
packet waves on the coordinator with no auxiliary work. It demonstrated route
use, not useful multi-packet scaling. Tiny/light CPU draws remain unsolved.

<!-- CodexAstraLocal: Remove only preparation with a proved absent consumer;
the packet that actually executes still retains its complete input recipe. -->
The CPU queue's temporary mapping validator no longer selects an input recipe
that it never uses. All mapping/range checks remain, and the owned execution
packet still prepares its full recipe. This small cleanup has no measured cost
or throughput claim and does not change the queue's scheduling boundaries.

Generic per-pixel shader decisions are a separate hypothesis, particularly at
higher resolution. Fragment processing was already on the GPU; this candidate
prepares more of its fixed control state on the CPU. It is not a substitute for
the portable CPU scheduling work or evidence that idle CPU capacity solves a GPU
limit. Driver busy samples do not measure app-only GPU time or DDR bandwidth.

Finite generator controls compare the intermediate, generic and fully specialized
routes using original synthetic state and CPU vertex transport. Cache and real
worker controls cover exact keys, tier pressure, retained full promotion, ready
priority, runtime-state changes, failures and retirement. Existing shader, Android,
package, signing and publication checks remain mandatory. A fresh CMake configure
refreshes the inherited source-derived shader-cache version before a reused build.

Target .40 speed, stutter, visual output and driver-memory behavior are pending.
No sustained 99% result, memory improvement or beta milestone is claimed. After
the authorized .40 consolidated tests, pause non-architecture work and report
the qualified best/slowest intervals and CPU/GPU/memory context. Unavailable DDR
and hardware-stall counters remain unavailable.
