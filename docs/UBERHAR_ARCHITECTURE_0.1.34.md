## Calculated isolation exposes the coverage gap

Strict Calculated now consumes unsupported guest batches without graphics fallback. It clears consumed vertex storage, cancels framebuffer invalidation for omitted work and cannot trigger a false-return graphics retry. Absent compute owners and missing targets also remain isolated. Incompatible backend selection reaches contained frontend failure. Other modes retain complete fallback behavior.

The single .33 strict launch reported 837,453 attempts, all explicitly omitted for unsupported state, with zero guest compute or graphics draws. Its blank guest output is a successful isolation observation and a failed rendering-coverage result. The .34 launch likewise records 1,032,364 unsupported-state omissions and zero guest compute/graphics draws. Neither is eligible for a complete-title speed comparison. CPU input loading, JIT, output conversion and assembly still execute; presentation, surface utilities and graphics preparation also remain. This is neither independent compute vertex execution nor a general compute renderer.

The .32 masked/endpoint rectangle extension had established exact synthetic pixel work but admitted no observed title state. Strict isolation does not broaden that subset. Another geometry relaxation would not explain an earlier state rejection; relevant exact failed state is required before another narrow admission hypothesis.

## Scratch measurements have a separate contract

The optional Android scratch request compares production rectangle commands with a graphics reference using original 88-byte CPU vertices and production shaders. It covers two extents and two nonzero masks, eight alternating-order pairs per case, with 32 operations per route. These are supported fragment workloads, without guest shader execution.

A create-only claim precedes preparation. Only one pair can be in flight; readback reuse requires accepted submission, GPU completion and coherent host access. Full-image comparison checks an independent expected pattern, including disabled channels and ordered overlap. All 64 routes must validate before ratios. Deadline or ownership changes stop admission without releasing queued resources prematurely; existing drain handles teardown. Graphics state is explicitly dirtied afterward. Synthetic commands never enter guest coverage counters.

GPU TOP-to-BOTTOM intervals include route barriers: one graphics pass or 32 compute dispatches. Reset/upload/readback, compilation and host enqueue/validation are separate. Ratios describe those complete synthetic routes, not exclusive kernels, per-draw guest cost or title speed. Partial counters describe observations before reporting; pending work may subsequently finish.

The .33 request failed preparation because its explicit Vulkan macro conflicted with the production compiler's definition. No route or pixel completed and no ratio exists. The .34 correction removes only that redundant preamble. Its new gate links the unchanged production compiler and actual extracted generation/call, validates all three stages across four profiles, and rejects the original defect. This closes the modeled-preparation/standalone-validator gap for the explicitly optimizer-disabled path.

The actual .34 request then completed all 32 pairs, 64 routes and 2,048 operations, with source-bound owner image checks and available timestamps. Median paired compute/graphics route ratios are **0.9050/0.9264** for 256×256 full/R+B writes and **1.0054/1.0068** for 800×480 full/R+B writes. Thus the small supported workloads favor compute in this run; larger workloads are slightly slower. This demonstrates real target kernel work and its bounded measurement path, while title coverage remains zero. Repeated writes are idempotent, so final pixel equality alone is not a per-operation trace. Preparation and host costs, order-specific ranges and lifecycle limits remain in the test review; these ratios cannot be applied to the title's CPU vertex wall.

## Input recipes preserve the whole CPU execution contract

The input plan already prepared format readers once per draw. Four exact, complete, default-free recipes now replace repeated per-attribute reader dispatch. They retain the same typed conversions, live addresses, strides, register destinations and ascending alias order. Preparation resets executor and tag before failure or retry; range mapping and live-index rescue remain. Unmatched plans use the existing generic loader.

One live ShaderUnit, both output banks, FIFO invocation order and persistent primitive tails are unchanged. There is no cross-draw payload cache, new mapping, allocation or worker. Bounded shape recognition, a per-miss dispatch and code growth are real costs; host wins on selected synthetic layouts do not predict target benefit.

Five counters add 40 bytes and consume actual completed no-GS input invocations once per draw. Their sum equals fused transport; fused plus legacy equals native conversions in that branch, not every geometry/virtual shader invocation. There is no new per-vertex accounting or log. The device reader reports lifetime counts and fully contained spans between delivered snapshots, without inventing a report cadence or treating lost reports as zero. Actual Native evidence now establishes reach: four complete recipes handled 759,361,942 of 878,445,968 completed input invocations (86.44%) across 37 fully contained delivered snapshot spans. Two spans bridge missing interior reports; their boundaries are not reconstructed. Combo separately records 596,612,086/706,532,601 complete-recipe invocations (84.44%) across 37 contained delivered spans. Lifetime coverage is a different population, including menus and exit. These counts establish use, not saved time, and cannot weight synthetic timing ratios.

## Performance direction and inherited obligations

The .34 Native opening reports 29.33% mean logged speed and a 21.38% wall-weighted p05 over reporting-window averages, far below 99%. Its separate inclusive LoadVertices bracket is 168.00/204.15 seconds (82.29%). Combo reports 26.24% mean speed, 20.24% p05 over window averages and a 1,012.49 ms worst interval; its inclusive bracket is 137.14/203.07 seconds (67.53%). That stall survives the no-video/no-observer subset. These unlike controls do not measure a Native/Combo gain. The .33 Native and Combo brackets were about 82.44% and 66.89% of separate reporting wall. That path ends before DrawTriangles and includes preparation, transport, JIT, output/FIFO/assembly and intervening scheduling. It is not exclusive shader CPU time; the remainder is not GPU time. The .29–.32 decline and cooler .33 rebound remain causally unassigned. Unequal scenes, process order and conditions prevent a version-gain conclusion.

The two finite Combo activity windows add a different measurement: the dominant emulation thread accounts for roughly 77–99% of one core, while whole-system execution is about 16–32% of accounted core time. GPU driver-window samples are often high (78–100%), with reported clocks changing between 475, 550 and 680 MHz. CPU and GPU work overlaps; these values cannot partition a frame or prove maximum arithmetic capacity. Sparse frequency and last-CPU endpoints are not residency. A CPU optimization can matter to Native while Combo also needs GPU-cost investigation; neither unused cores nor a high busy counter supplies a speedup bound.

After the requested stop, the ranked decisions are:

1. **Keep the .34 verdict narrow.** The valid scratch population demonstrates supported work on device, and recipe counters demonstrate actual CPU-path reach. Strict title compute coverage is still zero and sustained speed is unqualified. A next performance candidate needs an exact complete-path experiment; neither kernel ratios nor invocation counts supply its benefit.
2. **Prioritize a larger exact CPU vertex improvement.** A concrete source-only lead is A64 same-instruction partial output writeback with raw lane/half stores, preserving disabled bits, aliases, current output bank, every FP instruction and arbitrary entry/control semantics. The retained 157 static sites are not executed counts. Actual A64 differential execution and whole-loop performance, including store forwarding and code size, would be required before selection. The stopped ABI harness is not reopened.
3. **Treat independent Calculated rendering as a substantial architecture project.** Ordered triangles, clipping/interpolation, texture/TEV/lighting, depth/stencil/blend, numerical modes and surface ownership need an executable baseline. Parallel vertices additionally require carry independence and exact input/FIFO/quaternion behavior. Existing conservative certificates and already-promoted unlit captures do not establish those prerequisites. Compute vertices followed by graphics fragments would be a separately named hybrid, not strict Calculated completion.

Unresolved inherited issues remain distinct from observed causes: bounded terminal handling for unexpected descriptor allocation errors; fence-worker teardown/publication ordering; cache clearing versus live handle ownership; the capture label for required specialized recovery; and accelerated Strip/Fan tail transfer. None is established as the cause of current glitches, slowdown or memory growth. Fixed owner counts also do not bound opaque driver residency; longer active growth and pressure remain open.

The inherited **A64 main-return sentinel mismatch is confirmed by source and retained emitted-code evidence**. Main writes its sentinel at SP+8, but the return check reads saved caller X19 at SP+16. A static, ABI-permitted counterexample takes RET before restoring the stack and registers. Active CALL frames correctly use SP+16, so changing that offset alone would break their contract. X19 and SP preservation are required by [AAPCS64](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst#general-purpose-registers). The relevant implementation is unchanged across the reviewed releases; actual ARM occurrence and title impact remain unproven. No runtime harness or repair is included in .33/.34.
